BELIARDO PROJECT SUMMARY
Last reviewed: 2026-08-27

PURPOSE AND REAL-WORLD OPERATION
Beliardo is a multi-tenant lounge operations SPA for billiard, ping-pong, and PlayStation venues. An approved owner configures stations, invites employees, runs live sessions, and reviews daily/monthly/yearly performance. Employees receive restricted Home access to operate sessions. Platform administrators approve and manage tenant accounts. Session timestamps are stored in UTC; tenant timezone rules assign reporting dates. A business day runs from 06:00 local time through the instant before 06:00 the next calendar day.

ARCHITECTURE AND STACK
- Frontend: React 18 SPA, Vite 5, Recharts, browser Fetch API, Supabase JS client. Source is under frontend/src; production output is frontend/dist.
- Backend: Node.js ES modules, Express 4, controller -> service -> repository layering under backend/src/features.
- Data/auth: Supabase Auth plus PostgreSQL. The backend uses a server-only service-role client; browser authentication uses the public Supabase client.
- Database: businesses, business_members, profiles, platform_admins, stations, sessions, employee_invitations, and admin_audit_logs. Migrations are in backend/supabase/migrations. RLS protects direct authenticated access; backend repositories use explicit tenant filters while operating with service-role privileges.
- API: JSON REST under /api. Main groups are /health, /access, /platform, /employees, /stations, /sessions, /dashboard, and /business.
- Testing: Node's built-in test runner with repository fakes/unit tests. There is no live Supabase integration suite, browser E2E suite, or CI configuration.

AUTHENTICATION, ACCESS, AND ROLES
- Supabase provides sign-up, email confirmation, password sign-in, password reset, invitation/recovery links, sessions, and token verification.
- Every protected backend request uses Supabase getClaims() to cryptographically verify the bearer token. Asymmetric tokens verify locally with cached JWKS; symmetric tokens safely fall back inside Supabase Auth to getUser(). Only the verified subject establishes identity. One service-role-only SQL function then loads the database profile/email, platform-admin flag, tenant membership, tenant status, role, and timezone; JWT/client claims never grant application roles.
- platform_admin: platform-wide user/owner approval, suspension, reactivation, removal, and audit APIs.
- owner: full access only when profile, tenant, and membership are approved/active; can configure stations, manage employees, operate sessions, and view analytics.
- employee: active-tenant Home/session access; cannot manage stations, employees, or analytics. New invitees must finish password setup before Home access.
- Additional states block access: pending_email, pending_approval, rejected, suspended, deleted, disabled membership, inactive tenant, and password_setup_required.
- If multiple memberships exist, the API supports X-Business-Id, but the current UI has no tenant switcher and otherwise uses the first eligible membership.

MAIN WORKFLOWS
1. Owner onboarding: sign up -> confirm email -> database creates pending owner/profile/tenant -> platform admin approves -> owner configures stations.
2. Employee onboarding: owner creates invitation -> only a SHA-256 token hash is stored -> Supabase sends invite or recovery email -> authenticated recipient accepts via atomic SQL RPC -> employee membership/profile activate -> password setup completes -> Home opens.
3. Station management: owner edits the station list; frontend caches per tenant in localStorage and syncs the authoritative list through the backend.
4. Session lifecycle: create draft -> start -> optional pause/resume/update -> end, or cancel an active/paused session without billing. Elapsed duration excludes paused time; final cost is derived only when ending normally. Cancellation is auditable and atomically returns the station to available without entering completed history or reports.
5. Reporting: completed sessions feed dashboard and business analytics. Daily history includes completed sessions ending in the selected business day and active/paused sessions overlapping it. Monthly/yearly totals and charts group by the tenant business date.
6. Business-day rollover: backend returns the authoritative business date and next 06:00 UTC instant. An open Home page refreshes at that boundary; active sessions remain open, while the Finished counter resets for the new day.

BUSINESS-DAY AND REVENUE RULES
- BUSINESS_DAY_START_HOUR in backend/src/shared/utils/timeRange.js is the single application cutoff constant.
- Tenant-local times before 06:00 receive the previous calendar date; 06:00 starts the new date.
- Query windows are half-open [local 06:00, next local 06:00), converted to UTC. This handles DST days with 23 or 25 elapsed hours.
- Date-only API filters normalize to those tenant-local boundaries. Explicit timestamp filters remain exact UTC instants.
- The cutoff value is passed to the database analytics RPC; reusable SQL business_date() performs database grouping without a separate hardcoded cutoff.
- Existing revenue recognition is preserved: a completed session's full final duration and cost belong to the business day in which it ends. Sessions are not split or automatically ended at 06:00. Concurrency charts clip overlap only for visualization.

Station cards use a local, dimension-reserving skeleton only when no tenant-keyed cache is available; header counters remain placeholders until their source request resolves instead of briefly showing incorrect zeroes.

Backend-only or incomplete:
- Platform audit-log and some user-update APIs exist, but the current platform UI does not expose the full audit log or profile-edit workflow.
- /api/dashboard and /api/sessions/completed exist, while the main frontend primarily uses /api/business summaries and the daily ledger rather than dedicated screens for every endpoint.
- No PDF/CSV/data export implementation exists.
- No scheduled end-of-day aggregation exists; reports are computed on demand. No active session is auto-ended.
- No realtime/WebSocket subscription or multi-client conflict resolution; synchronization occurs through REST and the scheduled 06:00 refresh.
- Currency is currently fixed to USD in business summaries rather than stored per tenant.
- No pagination UI; several repository/API reads use fixed limits.
- No runtime feature is intentionally mocked. Unit tests use in-memory repository fakes.

KNOWN ISSUES, TECHNICAL DEBT, AND SECURITY RISKS
- Migration dependency: deployed Supabase schema must include every migration through 20260827_011. Migration 010 is required by authentication; migration 011 adds cancelled session audit fields/status and the service-role-only atomic cancellation function.
- The frontend environment example currently contains project-specific public Supabase configuration instead of neutral placeholders. Replace it with placeholders and review/rotate exposed project credentials according to Supabase policy. Never place the service-role credential in frontend code.
- Internal database error messages are exposed whenever NODE_ENV is not exactly production. Production deployment must set NODE_ENV=production.
- No API rate limiting, brute-force protection, request correlation, structured logging, or centralized monitoring is implemented. Supabase provides some auth-provider controls, but application endpoints remain unthrottled.
- Invitation tokens travel in a URL query parameter until acceptance, creating potential browser-history, referrer, proxy-log, and screenshot exposure. Tokens are random, expire, and are stored hashed, but URL handling should still be hardened.
- The service-role client bypasses RLS, so every repository and access guard must retain explicit tenant scoping. A guard/repository regression could have high impact.
- Session update plus station-status update, station list upsert plus deletion, and several platform status transitions are multi-step operations rather than database transactions; partial failure can leave inconsistent state. Invitation acceptance is atomic.
- Station localStorage fallback treats an empty remote station list as potentially unavailable and can repopulate it on the next owner sync. Empty authoritative lists and offline failures should be distinguished.
- Tests do not execute migrations or repositories against PostgreSQL/Supabase, so SQL syntax, permissions, RLS, and deployment drift require manual verification.
- Frontend uses the official standalone @supabase/auth-js client because it does not call Supabase database, storage, functions, or realtime APIs directly. Session persistence, automatic refresh, URL callback handling, and the existing auth API remain intact. Analytics, admin pages, session controls, and station forms are lazy-loaded; the optimized initial chunk is 278.38 kB (80.15 kB gzip).

The Hall operations h1 has no opacity, visibility, transition, or entrance animation, and no remote/@font-face resource blocks it. It uses the system fallback stack.
- Baseline contributors after the required security gate were eager parsing of Dashboard, Employees, Platform Admin, session controls, and station forms; serialized /api/stations then /api/sessions/active startup; repeated development-mode GETs; three separate database context reads in authentication; and a 250 ms clock update at the application root.
- Initial production API counts remain one /api/access/me, one /api/stations, and one /api/sessions/active request. The station and session requests now begin concurrently. Under React development StrictMode, overlapping duplicate GETs that could previously issue twice are coalesced to one in-flight request per authenticated token and path.

Code tracing confirmed that every endpoint paid a remote auth.getUser() verification before the access-context RPC; getClaims() now removes that remote verification only when the deployed project uses asymmetric signing. Exact stage timings and post-change endpoint timings remain unmeasured because no authenticated test session or database EXPLAIN access was available.
- Migration 010 matches the real filters: business_members(user_id, joined_at) excluding removed memberships and active/paused sessions by business_id/started_at. The existing station uniqueness index already supports business_id/type/number ordering, so no redundant station index was added. Stations and sessions began concurrently and did not block the authorized heading.
